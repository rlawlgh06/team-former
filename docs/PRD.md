# PRD — 팀 편성 웹 앱

학생이 팀 프로젝트의 팀을 스스로 편성하고, 마감 뒤 남은 학생은 AI가 배정하되 앱이 그 배정을 규칙으로 검사하는 웹 앱.

- 과목 중간 과제 (배점 30점), 마감 2026-11-02 23:59
- 기술: Streamlit + Supabase(PostgreSQL) + OpenRouter
- 3장 기능별 해결은 **전부 어려운 해결**을 선택함 (9절)

---

## 1. 목적과 성공 기준

### 목적

학생이 서로 지원·투표로 팀을 만들고, 남은 학생은 AI 배정으로 메우되, 팀 구성 규칙을 앱이 끝까지 보장한다.

### 성공 기준

1. 자동 채점 프로그램이 멈추지 않고 끝까지 조작할 수 있다 — 2.7절 `key` 를 하나도 틀리지 않음
2. 확정된 팀 구성이 **항상** 4절의 규칙을 모두 지킨다 — AI가 실패하든, 모든 모델이 죽든
3. 규칙을 지키는 배정이 수학적으로 존재하지 않으면, 억지로 배정하지 않고 그 사실과 이유를 알린다
4. 키·관리자 비밀번호·실명이 저장소와 화면에 없다

### 성공으로 보지 않는 것

- AI가 "좋은" 배정을 내는 것 — 채점은 AI 답의 품질이 아니라 **규칙 준수와 실패 처리**를 본다
- 화면이 보기 좋은 것 — 채점 프로그램은 `key` 로만 요소를 찾는다

## 2. 사용자

| 사용자 | 로그인 | 하는 일 |
| --- | --- | --- |
| 학생 | 학번 + 비밀번호(`1234`) | 팀 목록과 팀원의 주·보조 역할 보기, 팀 지원, 내 팀에 들어온 지원에 찬성/거부 |
| 관리자 | 학번 `admin` + `ADMIN_PASSWORD` | 명단 CSV 올려 초기화, 모집 마감, AI 배정 실행, 배정안 확정 |

- 여기서 "학생"은 명단 CSV 에 든 **가상 학생**이다. 실제 사람의 이름·학번은 쓰지 않는다
- 관리자 계정은 앱이 시작할 때 `ADMIN_PASSWORD` 로 만들거나 비밀번호를 갱신한다. 명단을 다시 올려도 관리자 계정은 남는다
- 학생 계정으로는 관리자 기능에 접근할 수 없다 (감점 11번)

## 3. 데이터

### 역할 6개

기획자(PL), 웹 프로그래머(WP), 프론트엔드 디자이너(FD), 테스터(TT), 보고서 작성자(RW), 발표자(PT)

학생마다 **주 역할 1개**와 **보조 역할 0~2개**가 명단에 정해져 있고, 학생이 바꿀 수 없다.

### 명단 CSV (UTF-8, BOM 허용)

```csv
student_no,name,main_role,sub_roles
2026001,가나다,기획자,보고서 작성자
2026002,라마바,웹 프로그래머,
2026003,사아자,테스터,기획자;발표자
```

- `utf-8-sig` 로 읽어 BOM 을 처리한다
- `sub_roles` 는 `;` 구분, 없으면 빈칸
- 6개 역할 밖의 값, 주 역할 누락, 학번 중복은 오류로 거부하고 이유를 보여 준다

### 명단 올리기 = 초기화

명단 CSV + 팀 수를 받으면 지원·투표·팀원·마감 표시를 모두 지우고, 명단의 학생과 빈 팀(팀1 … 팀N)을 새로 만든다. 관리자 계정만 남긴다.

## 4. 규칙

### 4.1 확정된 팀 구성이 지켜야 할 것

| 규칙 | 내용 |
| --- | --- |
| 인원 | 모든 팀이 2~4명 (빈 팀 없음) |
| 주 역할 중복 | 주 역할이 같은 학생이 한 팀에 2명 이상이면 안 됨 |
| 필수 포함 역할 | 모든 팀에 기획자 1명과 웹 프로그래머 1명이 **서로 다른 사람**으로 있어야 함. 주 역할이든 보조 역할이든 맡을 수 있음 |

- **주 역할**은 팀 안의 중복을 따지는 기준
- **보조 역할**은 필수 포함 역할을 맡을 수 있는지 따질 때만 쓴다

### 4.2 필수 포함 역할 자리 계산 — 핵심 알고리즘

기획자와 웹 프로그래머를 **서로 다른 사람**이 맡아야 하므로, "기획자를 할 수 있는 사람이 있나" 를 각각 세면 틀린다. 한 사람이 둘 다 할 수 있어도 하나로만 센다.

팀원 집합에 대해 `{기획자, 웹 프로그래머}` 와의 **최대 이분 매칭**을 구한다. 필수 역할이 2개뿐이므로 다음으로 충분하다.

```
채운수(팀원) =
    0  — 기획자도 웹프로그래머도 맡을 수 있는 팀원이 없음
    2  — 두 역할을 서로 다른 두 사람에게 동시에 배정할 수 있음
    1  — 그 밖 (맡을 수 있는 사람이 있으나 2명을 못 채움)
```

지원을 막는 조건:

```
남는자리 = 4 - (팀원수 + 1)            # 지원자가 들어간 뒤
못채운수 = 2 - 채운수(팀원 + 지원자)
if 남는자리 < 못채운수:  막음
```

공고의 두 예시가 이 식으로 설명된다.

- 주 역할 기획자 + 보조 역할 웹 프로그래머인 학생 혼자 있는 팀 → `채운수 = 1` (한 사람이 둘 다 할 수 있어도 1)
- 테스터와 발표자만 있는 2명 팀에 보고서 작성자가 지원 → 남는자리 1, 못채운수 2 → **막음**

### 4.3 지원

지원 단추를 누른 순간 앱이 검사한다. 접수하지 않으면 **막힘**이고 투표 없이 끝난다.

| 막는 이유 | 처리 |
| --- | --- |
| 이미 팀이 있음 | 단추를 숨기거나 비활성화 (2.8절) |
| 결과를 기다리는 지원이 있음 | 단추를 숨기거나 비활성화 |
| 모집이 마감됨 | 단추를 숨기거나 비활성화 |
| 팀이 꽉 참 (4명) | "막힘: 팀이 꽉 찼음" |
| 같은 주 역할의 팀원이 있음 | "막힘: 같은 주 역할의 팀원이 있음" |
| 필수 포함 역할 자리가 모자람 (4.2절) | "막힘: 필수 포함 역할을 맡을 학생의 자리가 모자람" |

한 학생은 지원 결과(승인 또는 거절)가 나오기 전에 다른 팀에 지원할 수 없다. 결과가 나온 뒤에는 다시 지원할 수 있다.

### 4.4 투표

| 상황 | 결과 |
| --- | --- |
| 빈 팀에 지원 | 투표할 팀원이 없으므로 **바로 승인** |
| 팀원이 있는 팀에 지원 | **대기**. 그 팀의 팀원 모두가 투표함 |
| 모든 팀원이 찬성 | 승인 직전 재검사(4.5절) 통과 시 **승인** |
| 한 명이라도 거부 | 다른 팀원의 투표를 기다리지 않고 **바로 거절** |
| 아직 투표하지 않은 팀원이 있음 | **대기** |

- 투표할 사람은 **투표하는 때의 팀원**이다. 내가 지원한 뒤 다른 지원자가 먼저 승인되어 팀원이 되면, 그 사람도 내 지원에 투표한다
- 한 번 투표하면 바꿀 수 없다
- 이미 투표한 지원에는 찬성·거부 단추를 숨기고 "내 투표: 찬성" 처럼 보여 준다

### 4.5 승인 직전 재검사

같은 팀에 대기 중인 지원이 여럿이면, 앞의 지원이 먼저 승인되어 팀 구성이 바뀐다. 따라서 **모든 팀원이 찬성해 승인하려는 순간** 규칙을 다시 검사한다.

- 검사 항목: 정원, 주 역할 중복, 필수 포함 역할 자리 (4.2절)
- 위반하면 그 지원은 **거절**하고 이유를 보여 준다
- 그 전에는 대기 중인 지원을 미리 거절하지 않는다
- 처리 순서는 지원한 순서가 아니라 **투표가 끝난 순서**다
- 검사와 팀원 추가는 하나의 트랜잭션 안에서 한다

### 4.6 마감과 배정

1. 관리자가 "모집 마감" → 이후 지원·투표 불가
2. 마감 때 **대기 중인 지원은 거절**된다. **1명뿐인 팀의 학생은 팀에서 빠져** "팀이 없는 학생"이 된다
3. 관리자가 "AI 배정" → 앱이 현재 팀 구성, 팀이 없는 학생과 그 역할, 4.1절 규칙을 AI에 보내 배정안을 받는다. **팀이 없는 학생만** 넣고, 이미 팀에 있는 학생은 옮기지 않는다
4. 앱이 배정안을 다섯 가지로 검사한다
   1. 팀이 없는 학생이 빠짐없이 배정됨
   2. 한 학생은 한 팀에만 배정됨
   3. 모든 팀이 2~4명
   4. 팀 안에서 주 역할 중복 없음
   5. 필수 포함 역할 충족
5. AI 가 무응답·빈 응답·오류를 내거나 4항 검사를 통과하지 못하면 2차 → 3차 모델로 넘어간다. 모델마다 **전체 대기 120초**를 넘기면 끊는다
6. 3차까지 실패하면 앱이 스스로 배정한다 (완전 탐색)
7. 검사를 통과한 배정안만 관리자에게 보여 준다. 확정하면 DB 에 저장한다
8. 규칙을 모두 지키는 배정이 **존재하지 않으면** 배정안을 만들지 않고 "규칙을 지키는 배정이 없음" 과 이유(예: 팀3에 웹 프로그래머를 맡을 학생이 없음)를 보여 준다. 이때는 AI 를 부르지 않는다

> 8항을 먼저 판정하므로, 애초에 해가 없는 상황에서 무료 모델 호출 한도를 낭비하지 않는다.

## 5. 결과 안내 규약

`result` 컨테이너의 안내는 네 단어 중 하나로 시작한다. 채점 프로그램은 **첫 단어만** 본다.

| 첫 단어 | 뜻 |
| --- | --- |
| `승인` | 지원이 승인됨 / 관리자 동작을 해냄 |
| `대기` | 지원이 접수되어 투표를 기다림 |
| `거절` | 접수된 지원이 팀원의 거부·승인 직전 검사·마감으로 떨어짐 |
| `막힘` | 지원을 아예 접수하지 않음 / 관리자 동작을 하지 못함 |

예: `막힘: 같은 주 역할의 팀원이 있음`, `승인: 모집을 마감함`

**막힘과 거절의 차이**: 막힘은 접수조차 하지 않은 것, 거절은 접수되어 대기 중이던 지원이 떨어진 것.

## 6. 화면

### 6.1 요소 key (2.7절) — 하나도 틀리면 안 됨

| 화면 요소 | Streamlit 요소 | key |
| --- | --- | --- |
| 학번 입력칸 | `st.text_input` | `login_student_no` |
| 비밀번호 입력칸 | `st.text_input` | `login_password` |
| 로그인 단추 | `st.form_submit_button` | `login_submit` |
| 로그인한 사람 표시 | `st.container` | `whoami` |
| 단추를 누른 결과 안내 | `st.container` | `result` |
| 팀 하나의 표시 | `st.container` | `team_1`, `team_2`, … |
| 팀에 지원하는 단추 | `st.button` | `apply_1`, `apply_2`, … |
| 찬성 단추 | `st.button` | `vote_yes_{지원자 학번}` |
| 거부 단추 | `st.button` | `vote_no_{지원자 학번}` |
| 명단 CSV 올리기 | `st.file_uploader` | `admin_roster_file` |
| 팀 수 | `st.number_input` | `admin_team_count` |
| 처음 상태 만들기 | `st.button` | `admin_start` |
| 모집 마감 | `st.button` | `admin_close` |
| 팀이 없는 학생 표시 | `st.container` | `unassigned` |
| AI 배정 | `st.button` | `admin_assign` |
| AI 배정 진행 안내 | `st.container` | `assign_status` |
| 배정안 확정 | `st.button` | `admin_confirm` |

- `key` 는 영문·숫자·밑줄만 쓴다
- `refresh` 단추는 **두지 않는다** — 자동 갱신(어려운 해결)을 하므로
- 팀 번호는 관리자가 명단을 올릴 때 만든 팀1, 팀2… 의 번호이고 시나리오의 팀 번호와 같다

### 6.2 학생 화면

- 팀 목록, 각 팀의 팀원과 팀원의 주·보조 역할
- 내 팀을 구별되게 표시. 팀이 없으면 "아직 팀이 없음"
- 이미 팀에 속했거나 결과를 기다리는 지원이 있거나 마감되었으면 지원 단추를 숨김
- 내 팀에 들어온 대기 중 지원마다 찬성·거부 단추. 이미 투표했으면 "내 투표: 찬성"
- 바뀐 부분만 **3초마다 자동으로 다시 표시** (`st.fragment(run_every=3)`)

### 6.3 관리자 화면

- 명단 CSV 업로더 + 팀 수 + 처음 상태 만들기
- 모집 마감
- `unassigned` — 팀이 없는 학생의 이름
- AI 배정 → `assign_status` 에 진행 상황("1차 모델 응답 대기 중 (37초)", "2차 모델로 넘어감") → 배정안 표(학생 이름·역할·배정된 팀) → 확정
- 관리자 동작의 결과도 `result` 에 `승인` 또는 `막힘` 으로 시작해 보여 준다
- 마감 결과(대기 지원 거절, 1명 팀 해산)는 `unassigned` 로 확인된다

## 7. 비기능 요구사항

### 7.1 보안

- 비밀번호는 **bcrypt 해시**로 저장한다. 평문 저장 금지
- 로그인은 학번 + 비밀번호. 비밀번호가 틀리면 로그인되지 않는다. 학번만으로는 들어갈 수 없다
- 구글 로그인(`st.login`)은 쓰지 않는다 — 채점자가 학생 여러 명으로 로그인해야 하므로
- 학생 계정으로 관리자 기능을 쓸 수 없다. 관리자 화면은 `is_admin` 으로만 그린다
- `OPENROUTER_API_KEY`, `DATABASE_URL`, `ADMIN_PASSWORD` 는 `.env`(로컬) / Streamlit Secrets(배포)에만 둔다
- 키 값을 화면이나 로그에 출력하지 않는다. 존재 확인은 "있음/없음" 만 출력한다
- 명단·코드·문서·화면 캡처에 실제 사람의 이름·학번을 쓰지 않는다 (README 작성자 이름은 예외)

### 7.2 성능

- DB 연결은 **한 번만** 만들어 재사용한다 (`st.cache_resource`). 질의마다 연결을 새로 만들면 화면 한 번 그리는 데 몇 초가 더 걸린다
- Supabase 는 **Connection pooling 주소**를 쓴다. Streamlit Community Cloud 에서 직결(5432)이 실패하는 경우가 있다
- AI 배정 전체가 10분을 넘지 않는다 (감점 18번)

### 7.3 배포와 운영

- Streamlit Community Cloud 에 배포한다. Main file path 는 `streamlit_app.py`
- 깃허브 저장소는 마감까지 비공개, 11/3 09:00까지 공개로 바꾼다
- 배포한 앱은 "This app is public and searchable" 로 바꾼다. 로그인하지 않은 브라우저로 열어 로그인 화면이 보이는지 확인한다
- 테이블 이름은 모두 `tf_` 로 시작한다
- 테이블 DDL 을 `schema.sql` 로 남긴다 — 채점자가 DB 유일성 제약·테이블 이름·해시 열을 이 파일로 확인한다
- Supabase 일시정지를 막기 위해 **GitHub Actions 예약 작업**이 매일 DB 에 질의한다
- 화면에 시각을 보여 줄 때는 UTC 를 한국 시각으로 바꿔 보여 준다

### 7.4 AI 모델

- OpenRouter 의 무료 텍스트 생성 모델 3개를 1·2·3차로 정해 쓴다 (`:free`)
- 무료 모델 자동 라우터(`openrouter/free`)는 쓰지 않는다 (감점 14번)
- `reasoning effort` 는 `low`, `max_tokens` 는 넉넉히 — 추론 모델의 빈 응답을 줄인다
- 빈 응답도 실패로 보고 다음 모델로 넘어간다
- 무료 모델은 계정당 하루 50회·분당 20회. 채점 기간에 30회 이상 남겨 둔다

## 8. 데이터 모델

| 테이블 | 열 | 제약 |
| --- | --- | --- |
| `tf_students` | `id`, `student_no`, `name`, `main_role`, `password_hash`, `is_admin` | `student_no` UNIQUE, `main_role` CHECK (6개 역할) |
| `tf_student_sub_roles` | `student_id`, `role` | `role` CHECK (6개 역할), 학생당 0~2행 |
| `tf_teams` | `id`, `name` | `name` UNIQUE |
| `tf_members` | `team_id`, `slot_no`, `student_id` | PK `(team_id, slot_no)`, `student_id` UNIQUE, CHECK `slot_no between 1 and 4` |
| `tf_applications` | `id`, `team_id`, `student_id`, `status`, `reason`, `created_at` | `status` CHECK (대기/승인/거절) |
| `tf_votes` | `application_id`, `voter_id`, `vote` | PK `(application_id, voter_id)`, `vote` CHECK (찬성/거부) |
| `tf_settings` | `key`, `value` | PK `key` — 마감 여부 등 |
| `tf_ai_logs` | `id`, `tier`, `model`, `status`, `elapsed_ms`, `detail`, `created_at` | AI 호출 기록 (README 실패 사례 근거) |

제약이 규칙을 DB 수준에서 보장하는 부분:

- `tf_members.student_id` UNIQUE → 한 학생은 한 팀에만 소속
- `tf_members` PK `(team_id, slot_no)` + CHECK → 마지막 자리에 두 명이 동시에 들어가면 **먼저 도착한 학생만** 기록되고, 뒤에 온 쪽은 유일성 위반으로 거절된다
- `tf_votes` PK → 한 번 한 투표를 바꿀 수 없다

## 9. 고른 해결 방법 (3장 표)

| 기능 | 고른 것 | 어떻게 |
| --- | --- | --- |
| 다른 사람의 변경 보기 | **어려운 해결** (1점) | `st.fragment(run_every=3)` 으로 바뀐 부분만 자동 갱신. `refresh` 단추 없음 |
| 필수 포함 역할을 지킬 수 없는 팀 | **어려운 해결** (7점) | 지원 단계에서 4.2절 자리 계산으로 막음 |
| 같은 팀에 대기 중인 지원이 여럿 | **어려운 해결** (3점) | 승인 직전 트랜잭션 안에서 재검사, 투표가 끝난 순서로 처리 |
| 마지막 자리에 두 명이 동시에 들어감 | **어려운 해결** (0.5점) | DB 유일성 제약으로 먼저 도착한 학생만 기록 |
| AI 응답이 늦을 때 | **어려운 해결** (1점) | 모델마다 벽시계 전체 120초를 재서 끊고 다음 모델로 |
| 3차 모델까지 실패 | **어려운 해결** | 4.6절 4항 검사 다섯 가지를 모두 통과하는 배정을 백트래킹으로 완전 탐색 |
| AI 대기 중 화면 | **어려운 해결** (1점) | 몇 차 모델의 응답을 기다리는 중인지와 경과 시간을 표시 |
| DB 일시정지되지 않게 | **어려운 해결** (0.5점) | GitHub Actions 예약 작업이 매일 DB 에 질의 |
